**You already run Vexa. Tell us about your setup and we give you a bundle that works with what you already have.** If you're on 0.10, that means you're ready for 0.12. ([Install](install) is the other door — a cluster with nothing in it yet.)

## What we need to see

The shape of your environment, so nothing we ship asks for something you do not already have.

- **Your platform** — Kubernetes or OpenShift, which version, which cloud.
- **How the pieces are connected** — database and transcription: in-cluster or external, how each is addressed, which versions, and whether transcription runs on GPU or CPU.
- **What constrains the namespace** — resources and limits, quotas and LimitRanges, the node shapes you have.
- **What you run today** — image tags and the digests actually running, which names the jump.
- **What you have customised** — the values you set, so a bundle never overwrites a deliberate choice.
- **What you can reach** — Docker Hub directly, or only a mirror.

**Nothing about your data.** No schema, no rows, no transcripts, no credentials.

## The report

One command. It reads your namespace with `kubectl get` and nothing else: no database connection, no `exec`, no credentials.

```bash
python3 kit/report/vexa_state_report.py --namespace vexa --dry-run
```

`--dry-run` connects to nothing and writes nothing. It prints the exact commands a real run would issue, so you can hand that list to whoever owns the cluster before anything happens.

```bash
python3 kit/report/vexa_state_report.py --namespace vexa
```

The report is a directory of plain files with an archive beside it. `summary.txt` is the whole thing in plain English — read it first, open the raw files if you want to, then send the archive. The tool prints the path and stops; there is no transmit path in it at all.

The script is Apache-2.0 like everything here — if it misses something in your environment, patch it and send a PR.

## Then you send it

Open the files first. Send the archive by whatever means your policy allows. **We never see your environment — only the report you validated before sending.**

## What happens after

Your channel is set up for the shape the report describes. Its first entry is the current release with its evidence attached; the channel is private to you, and its contents are Apache-2.0 like everything else. Your staging pulls it, you check it in a real meeting, and you promote to production yourself. After that you stay current automatically — each release checked against your configuration before it reaches you.

Your database is not part of this. Vexa converges its own schema when it starts, so there is nothing for us to migrate and nothing of yours for us to touch.

## How we moved our own production onto the channel

**We did this to ourselves on 2026-08-25, and it is the same sequence your estate would follow.** Its shape is three commitments: the machinery goes in first and provably changes nothing, the takeover runs as a dry run before it is allowed to touch anything, and nothing is ever uninstalled. In order, with what we measured:

1. **Capture the before-state and take a fresh database snapshot** — pods, generations, the image-digest map, values, volumes — through the estate's own backup job.
2. **Install Argo CD with `resourceTrackingMethod: annotation` set before any Application exists.** This is what makes adoption non-destructive: Argo's default tracking writes its marker into the Deployment selector, which is immutable. Result: **13 of 13 generations unchanged** — it landed inert.
3. **Install Kyverno with zero policies**, so zero resource webhooks. Inert too; generations unchanged again.
4. **Install the contract and the channel public key** into the namespace.
5. **Create the Application with sync disabled, then read `argocd app diff`.** The fatal four — any selector, image or Secret difference — must be **zero**, and were. Residual label and tracking-annotation differences are expected: they are what adoption adds.
6. **Sync with ServerSideApply.** **36 of 36 pods kept their UID**, and the namespace held 111 ReplicaSets before and after — no pod template changed anywhere.
7. **Leave the Helm release secrets in place**, all 10 revisions of history intact. No `helm uninstall`, ever.

**Rollback exists at every step**: move the pin back and re-sync, or exit completely — delete the Application with `cascade=false`, then `helm rollback` — which leaves the estate exactly where it started, still owned by Helm.

Two that bite. **`--release-name` must match your existing Helm release** — Helm keys its release Secret on that name, and a mismatch installs a second copy of the whole estate beside the one you are running, against the same database. And **an estate with history usually has production and no staging**: `--staging-ns` and `--prod-ns` are separate namespaces here, so where your staging tier comes from is a decision to make before the Application exists.

**This has been done once, on our own Linode LKE production, and your environment is not that one.** The run is written up in full at [prod adoption](receipts/2026-08-25-prod-adoption); everything else that is and is not proven is at [what's proven, and where](tested).
