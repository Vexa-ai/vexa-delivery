**A deployment with history does not get upgraded before the upgrade has been rehearsed on a rebuild of it.** Every existing deployment starts here. ([Install](install) is the other door — a cluster with nothing in it yet.)

## The five steps

1. **You run a read-only script.** It writes a report — versions, migration revision, schema, a few aggregate counts. No data. You read it, then send it. The script is in the repo — if it misses something in your environment, patch it and send a PR.
2. **We rebuild exactly that state on our side** and rehearse your upgrade on it until it's green.
3. **Your channel's first entry is that rehearsed upgrade**, evidence attached. The channel is private to you; its contents are Apache-2.0 like everything else.
4. **Your staging pulls it**, you check it in a real meeting, you promote to production yourself.
5. **From then on you stay current automatically** — through the channel, or plain open-source images from Docker Hub, switchable any time.


**You need no more access than you already have to run your Vexa today. We build for what you have and deliver for that environment — if it's running 0.10, it's sufficient.**

## Step 1 — the report

```bash
python3 kit/report/vexa_state_report.py --namespace vexa \
  --db-host postgres.vexa.svc --db-name vexa --db-user vexa
```

It writes **`state-report.tar.gz`**, prints the path, and stops — exit codes `0` written · `2` usage · `3` redaction leak. Inside: **`workloads.json`** — image refs and the digests actually running, replicas, resources, Kubernetes version, node shapes · **`db.json`** — engine, extensions, per-table row counts, total size, and the migration revision where one exists — Vexa runs no Alembic, so on a Vexa estate that field is absent with its reason and the probes stand in for it · **`schema.sql`** — DDL only · **`probes.json`** — one aggregate count per known upgrade hazard, with the exact SQL printed beside its answer · **`runtime.json`** — the transcription reproduction surface · **`report.json`** — tool version, the source of every section, the redaction verdict.

**Without a database source every probe reports `not run`** — including the duplicate-key probe, which is the one that maps to an outage. The tool says so loudly rather than exiting quietly; the cluster half is still worth sending, but send it knowing that.

**No rows, no meeting content, no transcripts, no credentials.** Environment capture is allowlist-first; values under keys matching `password|token|secret|key|apikey` become `REDACTED`, and `--verify-redaction` (on by default) re-extracts the finished archive and exits `3` if one survived, naming files, never values. Reads are `kubectl get -o json` and nothing else. Every database session opens with `default_transaction_read_only=on`, and a probe is refused before it reaches a connection unless it is a single `SELECT count(...)`. There is no transmit path in the tool at all — no submit flag, no destination, no endpoint. Reaching the database costs one more decision and the default is **not** `exec`: `--db-host` needs no Kubernetes permission at all and is the one to try first; [`kit/report/job.yaml`](https://github.com/Vexa-ai/vexa-delivery/blob/main/kit/report/job.yaml) runs the whole report in-cluster under a read-only ServiceAccount when nothing routes to the database; `--db-pod` needs `create` on `pods/exec`, which most estates audit. Copy-pasteable Role and RoleBinding, written to be forwarded to whoever owns the cluster: [`kit/report/rbac.yaml`](https://github.com/Vexa-ai/vexa-delivery/blob/main/kit/report/rbac.yaml).

## Then you send it

Open the files first — they are plain JSON and plain SQL, and the tool stops instead of offering to help precisely so that reading them happens before anything leaves your perimeter. Send the archive by whatever means your policy allows, and the rehearsal starts from it. **We never see your environment — only the report you validated before sending.**


## How we moved our own production onto the channel

**We did this to ourselves on 2026-08-25, and it is the same sequence your estate would follow.** Its shape is three commitments: the machinery goes in first and provably changes nothing, the takeover runs as a dry run before it is allowed to touch anything, and nothing is ever uninstalled. In order, with what we measured:

1. **Capture the before-state and take a fresh database snapshot** — pods, generations, the image-digest map, values, volumes — through the estate's own backup job.
2. **Install Argo CD with `resourceTrackingMethod: annotation` set before any Application exists.** This is what makes adoption non-destructive: Argo's default tracking writes its marker into the Deployment selector, which is immutable. Result: **13 of 13 generations unchanged** — it landed inert.
3. **Install Kyverno with zero policies**, so zero resource webhooks. Inert too; generations unchanged again.
4. **Install the contract and the channel public key** into the namespace.
5. **Create the Application with sync disabled, then read `argocd app diff`.** The fatal four — any selector, image or Secret difference — must be **zero**, and were. Residual label and tracking-annotation differences are expected: they are what adoption adds.
6. **Sync with ServerSideApply.** **36 of 36 pods kept their UID**, and the namespace held 111 ReplicaSets before and after — no pod template changed anywhere.
7. **Leave the Helm release secrets in place**, all 10 revisions of history intact. No `helm uninstall`, ever.

**Rollback exists at every step**: move the pin back and re-sync, or exit completely — delete the Application with `cascade=false`, then `helm rollback` — which leaves the estate exactly where it started, still owned by Helm.

Two that bite. **`--release-name` must match your existing Helm release** — Helm keys its release Secret on that name, and a mismatch installs a second copy of the whole estate beside the one you are running, against the same database. And **an estate with history usually has production and no staging**: `--staging-ns` and `--prod-ns` are separate namespaces here, so where your staging tier comes from is a decision to make before the Application exists.

**This has been done once, on our own Linode LKE production, and your environment is not that one.** The run is written up in full at [prod adoption](receipts/2026-08-25-prod-adoption); everything else that is and is not proven is at [what's proven, and where](tested).
